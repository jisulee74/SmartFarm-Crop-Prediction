# 환경·제어 이력 기반 개체별 차기 착과수 예측 파이프라인 구현 계획

## Summary

2024-05-01 이후 데이터에서 `(user_id, sample_num, crop_sn, fruit_column)`별 현재·과거 생육정보와 `sfkr_hbfm_env_con`의 직전 1·3·7일 환경·제어 이력을 사용하여 동일 화방의 다음 조사 시점 `fruit_count`를 예측한다.

동일한 CatBoost 회귀 설정으로 다음 세 실험을 수행해 환경·제어 변수의 추가 가치를 검증한다.

1. 생육정보만 사용하는 Baseline
2. 환경·제어 정보만 사용하는 모델
3. 생육정보와 환경·제어 정보를 함께 사용하는 통합 모델

주 평가 지표는 Test MAE이며 RMSE, R², 화방별·사용자별 성능을 함께 산출한다.

## Implementation Changes

### 1. 원본 데이터 및 환경·제어 로그 감사

- 입력은 `data/control_log_period_splits/from_2024_05/{train,val,test}.parquet`으로 고정한다.
- `(user_id, sample_num, crop_sn, fruit_column)`을 화방 시계열 키로 사용한다.
- `sn`으로 `sfkr_pvsn_grow`의 생육 컬럼을 결합하고, `sfkr_pvsn_id`를 통해 `user_id → facility_id`를 검증한다.
- 환경·제어 로그는 `item_code='080400'`을 우선 사용한다. 해당 시설에서 빈 `item_code`만 존재하는 스트림은 별도로 표시해 허용하고 다른 작물 코드는 제외한다.
- 논리 센서 키는 `facility_id + fld_code + sect_code + fatr_code + maker_id + sen_id + meas_date`로 정의한다.
- 동일 논리 센서·시각 중복은 `sn`이 가장 큰 최신 행을 유지한다. 서로 다른 센서는 같은 시각이어도 중복으로 보지 않는다.
- `sen_val` 숫자 변환 성공률이 Train 구간에서 95% 이상인 `fatr_code`만 후보 변수로 사용한다.
- 센서 제조사나 ID 차이에 따른 열 폭증을 방지하기 위해 동일 시설·시각·`fatr_code`의 값은 중앙값으로 통합한다.
- DB 추출 결과는 Parquet으로 캐시하고 이후 feature/model 파이프라인은 DB 연결 없이 재실행할 수 있게 한다.
- 사용자별 로그 기간, 스트림 수, 수집 간격, 숫자 변환률, 장기 결측, 1·3·7일 coverage를 감사 산출물로 저장한다.

### 2. 동일 화방 차기 착과수 타깃 구성

- 각 화방 시계열을 `meas_date`순으로 정렬하고 다음 관측행을 연결한다.
- 입력 시점은 `feature_date`, 다음 관측일은 `target_date`, 정답은 `next_fruit_count`로 정의한다.
- 마지막 관측행은 다음 정답이 없으므로 제외한다.
- 서로 다른 `crop_sn`이나 `fruit_column` 사이로 타깃을 연결하지 않는다.
- 예측 표본의 split은 입력행이 아니라 `target_date`가 속한 기존 raw split으로 결정한다.
- Train 마지막 관측으로 Validation 첫 값을 예측하거나 Validation 마지막 관측으로 Test 첫 값을 예측하는 것은 허용한다.
- 모든 입력 변수는 `feature_date` 이하의 정보만 사용한다.

### 3. 생육 및 환경·제어 후보 변수 생성

생육 변수는 현재 조사 시점과 과거 방향으로만 계산한다.

- 현재 화방 착과수, 직전값, 변화량
- 최근 2·3·4회 평균, 표준편차, 최솟값, 최댓값, 변화 기울기
- 동일 개체의 1·2·3화방 현재값과 관측 여부
- `sfkr_pvsn_grow`에서 확보 가능한 엽장, 엽수, 엽병장, 관부직경, 화방수, 화수 등 현재값
- 조사 간격, 재배 시작 후 경과일, 현재 화방 첫 양수 관측 후 경과일
- 연중 주기 sine/cosine, 누적 관측 횟수
- `fruit_column`은 범주형 변수로 유지한다.

각 선택된 `fatr_code`에 대해 `feature_date` 직전 1일·3일·7일 구간에서 다음 변수를 생성한다.

- 평균, 중앙값, 표준편차, 최솟값, 최댓값
- 최초값, 최종값, 최초 대비 최종 변화량
- 시간 기준 선형 기울기
- 관측 수, 고유 관측시각 수
- 기대 수집주기 대비 coverage
- 최대 관측 공백 시간
- 설정값 변경 횟수와 값의 고유 개수

결측 정책은 다음과 같이 고정한다.

- 장기 공백을 가로지르는 보간은 하지 않는다.
- 일부 로그가 존재하면 관측된 값으로 통계를 계산하고 coverage 변수를 함께 제공한다.
- 구간 내 로그가 전혀 없으면 통계값은 Train 중앙값으로 대체하고 `missing` 플래그와 coverage 0을 유지한다.
- 대체값과 사용할 `fatr_code` 목록은 Train에서만 결정해 Validation/Test에 그대로 적용한다.
- 환경·제어 특징 이름과 원본 코드, 집계 창, 통계량을 feature manifest에 기록한다.

### 4. Ablation 학습 및 평가

세 실험 모두 동일한 표본, split, 전처리와 CatBoost 회귀 설정을 사용한다.

- `growth_only`: 생육·화방·시간 변수
- `env_control_only`: 환경·제어 통계와 coverage 변수
- `growth_env_control`: 두 변수군 전체

공통 모델 설정:

- `CatBoostRegressor`
- 손실함수 `RMSE`
- `iterations=2000`
- `depth=7`
- `learning_rate=0.03`
- `l2_leaf_reg=5`
- `random_seed=42`
- Validation early stopping 150회
- 사용자 ID, sample 번호, crop 번호 및 원본 센서 ID는 모델 입력에서 제외
- `fruit_column`만 범주형 변수로 허용

평가 절차:

- Train으로 학습하고 Validation MAE로 각 실험의 최적 반복 횟수를 결정한다.
- 결정된 반복 횟수로 Train+Validation을 다시 학습한다.
- Test는 최종 평가에만 사용한다.
- Persistence 예측인 `next_fruit_count = current fruit_count`와 Train 중앙값 예측을 별도 기준선으로 제공한다.
- 전체 및 화방별·사용자별 MAE, RMSE, R²를 산출한다.
- 통합 모델이 `growth_only`보다 Test MAE를 얼마나 개선하는지 절대값과 비율로 계산한다.
- 실제값–예측값, 화방별 시계열, 잔차 분포, 변수 중요도, 변수군별 ablation 비교 그림을 생성한다.
- CatBoost importance와 SHAP은 통합 모델에 대해서만 산출한다.

### 5. 실행 인터페이스와 산출물

진입점은 다음과 같이 구성한다.

```bash
python AXData/fruit_set_prediction/run_control_feature_pipeline.py
```

DB 원본을 다시 추출할 때만 다음 옵션을 사용한다.

```bash
python AXData/fruit_set_prediction/run_control_feature_pipeline.py --rebuild-env-cache
```

DB 접속정보는 `FARMSTOM_DB_*` 환경변수로만 받으며 코드에 비밀번호를 저장하지 않는다.

주요 산출물:

- `data/environment_cache/*.parquet`
- `processed_data/{train,val,test}_candidates.parquet`
- `artifacts/data_audit/`
- `artifacts/feature_engineering/feature_manifest.json`
- `artifacts/models/{growth_only,env_control_only,growth_env_control}.cbm`
- `artifacts/results/ablation_metrics.csv`

## Test Plan

- 동일 화방 안에서만 다음 관측값이 연결되는지 검증한다.
- 모든 예측 표본이 `target_date` 기준 split에 배정되는지 검증한다.
- 동일한 `user_id + sample_num + target_date`가 여러 split에 나타나지 않는지 검사한다.
- 환경 특징 계산에 `feature_date` 이후 로그가 한 건도 사용되지 않는지 검사한다.
- 1·3·7일 경계 포함 여부를 인위적 시계열로 검증한다.
- 논리 센서 중복 제거와 동일 `fatr_code` 중앙값 통합을 검증한다.
- 환경 로그 없음, 부분 coverage, 24시간 이상 공백 사례를 검증한다.
- Validation/Test의 대체값과 변수 목록이 Train에서만 결정되는지 검사한다.
- 세 ablation 데이터셋의 표본과 정답이 완전히 동일한지 검사한다.
- 고정 seed 재실행 시 split, 변수 목록, 최적 반복 횟수와 예측값이 재현되는지 검사한다.
- DB 캐시 실행과 캐시 재사용 실행의 processed dataset이 동일한지 검사한다.

## Assumptions and Success Criteria

- `sample_num`은 사용자·재배기간 내 동일 개체를 식별한다.
- 예측 대상은 동일 화방의 실제 다음 조사 시점 착과수이며 고정 7일 후 값이 아니다.
- 환경·제어 로그는 직전 1·3·7일만 사용하고 당일 미래 로그는 사용하지 않는다.
- 로그 coverage가 낮은 표본도 제거하지 않고 결측·coverage 정보로 표현한다.
- 모델별 튜닝 범위를 달리하지 않아 변수군의 효과를 공정하게 비교한다.
- 통합 명령이 중단 없이 완료되고 모든 표본에 NULL·무한대 타깃이 없어야 한다.
- Test는 특징 선택, 대체값 결정, early stopping 또는 모델 선택에 사용하지 않는다.
- 최종 보고서는 제어변수 추가 전후의 성능 차이와 사용자·화방·coverage 수준별 한계를 명시해야 한다.
- 핵심 성공 판단은 `growth_env_control`이 Persistence와 `growth_only`를 Test MAE에서 개선하는지 여부이며, 개선되지 않더라도 동일 조건의 ablation 결과를 그대로 보고한다.
